## 描述

实现路线图中的 F-005 书影音 `/media`：记录读过、看过、玩过的条目，整体参考 [pseudoyu · Media](https://www.pseudoyu.com/media?type=book)，从简。条目由作者在后台手动录入；录入表单上方有"识别"框，粘贴豆瓣分享链接后自动解析条目数据并填入表单（交互参考淘宝收货地址的"智能识别"）。不做豆瓣 RSS 同步、全量导入和定时任务。

> 2026-10-19 改方案：原计划"全量导入 + RSS 增量同步 + Cron"取消，改为手动录入 + 链接识别。文件名沿用 `media-douban-sync.md`，避免已有链接失效。

## 目标与验收

**目标**: 作者在后台快速录入读过、看过、玩过以及正在读 / 看 / 玩的条目，读者在 `/media` 按分类浏览。

**业务价值**: 作品集的一部分，展示作者的阅读和娱乐口味；粘贴一个豆瓣链接就能填好大部分字段，录入成本低，也不依赖豆瓣的非官方接口。

**验收条件**:
- [ ] 分类共 7 个：书 / 漫画 / 电影 / 剧 / 动画 / 游戏 / 桌游（book / comic / movie / series / anime / game / boardgame）；不做音乐
- [ ] 状态只有"读过 / 看过 / 玩过"和"在读 / 在看 / 在玩"两类，没有"想看"
- [ ] 后台录入表单字段：分类、标题、封面、作者 / 导演 / 开发商、年份、豆瓣链接（来自识别）；状态、我的评分（1–5，可空）、标记日期、短评（作者手动填）
- [ ] 识别：表单上方有识别框，粘贴豆瓣分享内容（纯链接，或 App 分享出来的"文字 + 链接"）后点"识别"，自动解析条目数据并填入表单；**只解析条目数据，不解析状态、评分、日期、短评**
- [ ] 识别结果可修改：填入后的每个字段都能手动改；识别不出的字段留空并提示；识别失败时表单照常可用，作者全部手动填写
- [ ] 按豆瓣条目 ID 去重：识别到已录入过的条目时提示，并提供"去编辑已有条目"
- [ ] 没有豆瓣链接的条目（识别失败、全部手填）也能保存；读者页上这类条目不可点击，不显示"豆瓣 ↗"
- [ ] 后台条目列表：可以编辑（含把"在读"改成"读过"）、隐藏、删除单个条目
- [ ] `/media` 用 Tab 切换分类；每行显示：封面、标题、作者 / 导演 / 开发商、我的评分；正在进行的条目加在读 / 在看 / 在玩标记；按标记日期倒序；有豆瓣链接的条目链接到豆瓣页
- [ ] 新增、编辑、隐藏、删除条目后触发 Deploy Hook，重建读者页

### 作者决定

| 事项 | 决定 |
|------|------|
| 数据来源（2026-10-19 修订） | 后台手动录入 + 豆瓣链接识别填表。不做豆瓣 RSS 同步、全量导入、Cron；不做 Steam / PS / Switch 同步；不做豆列批量导入、个人标记页抓取 |
| 识别范围（2026-10-19） | 只解析条目本身的数据：标题、封面、作者 / 导演 / 开发商、年份、分类、豆瓣链接与条目 ID。状态、评分、标记日期、短评由作者手动填 |
| 识别交互（2026-10-19） | 参考淘宝收货地址的"智能识别"，见下方"识别交互"。粘贴后不自动识别，点"识别"按钮才触发 |
| 无豆瓣链接的条目（2026-10-19） | 允许保存；读者页上该条目不可点击，不显示"豆瓣 ↗"；不参与按条目 ID 去重 |
| 分类映射 | 识别时自动判断，作者可在表单里改：剧 / 动画——豆瓣"电视剧"条目中，类型含"动画"的归动画，其余归剧；动画电影归电影。漫画——豆瓣"书"条目中带"漫画"标签的归漫画。桌游——豆瓣"游戏"条目按平台 / 类型字段识别（字段待 spike 确认） |
| 封面（2026-10-19 确认） | 采用**方案 C（转存 R2）**：因实际探测确认豆瓣 CDN 对外站及 `no-referrer` 均返回 418 拦截，保存条目时由后台 Worker 带豆瓣 Referer 下载封面并转存至 R2，读者端直接访问 R2 地址，彻底规避防盗链失效与图片损坏风险；条目删除时同步清理 R2 封面 |
| 页面形态 | 参考 pseudoyu：分类 Tab + 列表，不做条目详情页和年度统计 |

### 识别交互（参考淘宝地址识别）

| 环节 | 做法 |
|------|------|
| 位置 | 录入表单顶部的多行输入框，占位文字"粘贴豆瓣分享链接或分享文字，自动识别条目信息"，右侧"识别"按钮；粘贴后不自动识别，需点按钮 |
| 输入 | 可以是纯链接，也可以是 App 分享出来的整段文字；从文字中提取第一个豆瓣链接。App 分享链接形如 `https://www.douban.com/doubanapp/dispatch/movie/37501131`（2026-10-22 作者提供），直接解析出条目 ID，不做短链跳转 |
| 识别中 | 按钮显示加载状态，表单不锁定，作者可以继续手填 |
| 识别成功 | 把识别到的字段填入表单，被填入的字段短暂高亮；只覆盖识别到的字段，状态、评分、日期、短评不动；识别框下方提示"已识别：标题、封面、导演……" |
| 部分识别 | 识别不出的字段留空，提示"未识别：年份，请手动填写" |
| 识别失败 | 提示原因（不是豆瓣链接 / 链接打不开 / 解析不出），表单保持原样，可全部手填 |
| 重复条目 | 条目 ID 已存在时提示"这条已经录入过"，提供"去编辑"入口 |
| 清空 | 识别框带清空按钮；识别后可以再次粘贴识别，覆盖上一次识别的字段 |

### 技术风险（plan-tasks 时第一个做 spike）

- Cloudflare Worker 的出口 IP 可能被豆瓣拦截。如果被拦，退路是：识别失败时全部手填；或改为浏览器端打开链接、解析后回填（需评估跨域限制）
- 2026-10-19 实测结论：桌面端 `movie.douban.com` 存在人机验证挑战页；移动端 Rexxar 接口（`m.douban.com/rexxar/api/v2/...`）附带 Referer 可稳定拉取结构化 JSON 数据；豆瓣 CDN 图片直接引用或使用 `no-referrer` 均返回 418 拦截，故必须采用保存时转存 R2
- spike 还要确认：非影视类（书、游戏、桌游）在 Rexxar 接口下的可用性与字段映射；漫画标签和桌游字段能否识别；Worker 出口 IP 是否被 Rexxar 接口限制
- 命名：现有 `media` 领域指图片（见 [F-006 架构](../engineering/features/F-006-媒体存储清理/architecture/feature-architecture.md)），本 Feature 的 Domain 在 design-arch 时改名（如 `media-library` / `shelf`）

### 讨论记录

- 最初考虑同步 Steam / PS / Switch：Steam 有官方 Web API；PS 用非官方 psn-api，令牌几周就过期；Switch 只能用逆向的 nxapi，风险最高。作者最终决定只用豆瓣
- 封面比较过四种方式：A 直接引用、B Worker 代理、C 同步时转存 R2、D 构建时下载。成本都接近 0，A 最省事但最不稳，先用 A
- 2026-10-19 讨论链接解析：先比较了单个条目链接、豆列链接、个人标记页三种，一度定为"RSS 同步为主 + 单条 / 豆列链接补录"
- 2026-10-19 作者改方案：不做 RSS 同步、全量导入和豆列，只保留"粘贴分享链接识别"；只解析条目数据、不解析状态；识别结果填入手动录入表单，交互参考淘宝地址识别
- 2026-10-19 作者确认：无豆瓣链接的条目允许保存（读者页不可点击）；识别需手动点按钮，不在粘贴时自动触发
- 2026-10-19 封面方案确认：实测豆瓣 CDN 对 `no-referrer` 返回 418 拦截，作者确认采用方案 1（保存时转存至 Cloudflare R2），彻底避免裂图风险
